## Research question and starting evidence

Does a broader public-data sample change the relative performance and errors of the existing text classifiers, tree methods, and a pretrained structured-output model for the same four first actions?

M3 froze 400 accepted rows, 100 per class, in 360 groups. It used 242 training, 79 validation, and 79 sealed test rows. All 14 configurations ran twice and reproduced after archive restoration; validation-only selection chose L1-C10 with macro-F1 0.925 ([M3 record](evidence/m3-research-run.md)). That is an observed validation result on the old release, not a target or final-test result. Preserve the release, collection brief, splits, runs, and study-guide edition.

M3.5 has two changes: data scale/source coverage and model families. Rerun the existing matrix on the expanded split so classifier comparisons use the same data. Do not attribute a difference between old and new headline scores solely to extra training data: the validation population also changes. Any learning-curve analysis must hold the new validation set fixed and subsample training groups only; it is optional after the required comparison.

## 1. Establish public-source capacity before bulk collection

The October 31 plan set a minimum of **2,500 accepted rows** (625 per class), with **4,000 preferred** (1,000 per class). On November 1, after the source discovery found too few compliant lookups for 625 per class, Altan replaced it with a **2,000-row near-balanced working minimum**. Lookup may hold up to 500 rows with a floor of 350, and the other three classes are equal. Starting from 400, this requires 1,600 additional accepted rows. 2,500 and 4,000 remain aims that current evidence does not support. Report actual counts and the imbalance. These numbers are acceptance targets, not collected data. No class may be padded with duplicates, paraphrases, or unreviewed synthetic drafts to satisfy the total.

1. Screen unused eligible records in the adopted sources (Dolly, No Robots, BFCL, GSM8K), then additional public sources from the [research notes](evidence/m3-5-research-notes.md). Prioritize `knowledge_lookup` and `document_retrieval`: M3's lookup supply already needed AI drafts, and arbitrary QA questions do not automatically identify a document or database.
2. For each candidate source record its official URL, exact revision, license/attribution and redistribution conditions, human/generated origin, available fields, first-action mapping, exclusion rules, duplicate risks, and estimated eligible independent groups by class. Public availability alone is not permission. Source task labels are not Orchestra labels.
3. Use a fixed seeded screening order and record sampled/eligible/excluded counts and reasons. Estimate review workload from an observed small batch before promising the larger release. The source-size headline is not an eligible-row count.
4. Choose the collection target (the 2,000-row near-balanced minimum, or more if supply allows), source quotas and stop rule from capacity and review effort **before new model scores**. Record source adoption and the decision in a new versioned M3.5 collection brief; retain the old hash-bound brief unchanged. If no compliant mix reaches 2,000 with at least 350 lookups, report the shortfall and seek a scope decision; do not silently lower the minimum or start M4.

The new rows should come from compatible public data. Existing authored/AI rows remain with their provenance. Record public versus human-authored versus synthetic counts, since public datasets can also contain generated language. A further synthetic top-up is not part of this plan.

## 3. Implement a bounded, comparable experiment

The proposed matrix has **27 configurations**: the existing 14, four per new local classifier, and one fixed Jev setup. Freeze the exact resolved settings, versions, seeds, prompt/schema, budgets, and failure handling before the first M3.5 comparison. Capacity checks can change the proposal before that freeze, with a dated rationale; no unbounded search follows poor scores.

| Family | Input and proposed settings | Purpose |
| --- | --- | --- |

| Decision Tree (DT) | Same unigram TF-IDF as L2/S1; `max_depth` 10 or 30 × `min_samples_leaf` 1 or 3; `criterion="gini"`, seed 42. Four settings. | Test a single tree's feature interactions and sensitivity to tree size. |

## 4. Select and report without opening the test

Primary metric: validation macro-F1. Also save accuracy, per-class precision/recall/F1/support, confusion matrices, fit time, prediction latency and memory. For Jev report token/request cost, network latency, invalid outputs, timeouts, retries and coverage separately from local compute timings. Do not drop failed requests from the evaluation denominator or retry only incorrect predictions; freeze failure policy first and record predictions for every row.

Retain the 0.01 inclusive validation tie tolerance. For existing families retain the M3 rule. Within DT/RF ties prefer shallower depth, then larger minimum leaf size; unlimited depth ranks last. Within XGB ties prefer shallower depth, then lower learning rate at the fixed round count (a declared convention, not a complexity theorem). Record all per-family winners. For an overall choice use the predeclared order B0, B1, L1, L2, S1, L3, DT, RF, XGB, Jev within the tolerance, then prediction latency and configuration ID. This favors the established local workflow in near-ties, not a claim that it always generalizes better.

Run the local matrix twice and reproduce saved predictions/metrics from a restored archive. For Jev retain exact requests, responses, model ID, timestamps and usage in the local archive; cache verification is not an independent rerun. Include a budgeted repeat to measure disagreement, or explicitly report unavailable independent reproducibility. No model family can silently disappear: an access/resource failure leaves an open acceptance item until Altan records a scope decision.

Inspect validation errors and source-by-class performance to reveal source shortcuts, label ambiguity, and new failure patterns. A source-held-out or training-size analysis is optional and must use training/validation only with a recorded design. Do not promise that more rows or a more complex model improves macro-F1.
